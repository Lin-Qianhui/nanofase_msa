# Refactor Verification

This folder contains local-only regression checks for behavior-preserving migration
phases. The script runs a NanoFASE executable with a copied config and compares the
new outputs against a baseline generated by the original unrefactored model.

## Baseline Setup

The current `output/` directory can be used as the baseline if it was generated by
the original model from the tracked `config.nml`.

For exact checks, the baseline should come from the same compiler and build
settings used for the refactor comparison. If the baseline was produced from a
different source revision or build configuration, tiny floating-point formatting
differences may still cause a useful failure.

For a safer long-term baseline, copy it once:

```sh
mkdir -p verification/baselines/original_config_nml
cp -R output/. verification/baselines/original_config_nml/
```

`verification/baselines/` is ignored by git because the outputs are large.

## Run Verification

From the repository root:

```sh
python verification/verify_refactor.py \
  --exe build-debug/nanofase \
  --baseline verification/baselines/original_config_nml \
  --config config.nml
```

By default, numeric comparisons use:

```text
absolute tolerance: 1e-14
relative tolerance: 1e-12
```

Override those gates when a phase needs a documented tolerance:

```sh
python verification/verify_refactor.py \
  --exe build-debug/nanofase \
  --baseline verification/baselines/original_config_nml \
  --config config.nml \
  --atol 1e-12 \
  --rtol 1e-9
```

Use `--exact` to restore the original strict mode: CSV files must be
byte-identical, and filtered `summary.md`/`output.nc` text must match exactly.

You can also compare directly against the existing `output/` baseline:

```sh
python verification/verify_refactor.py \
  --exe build-debug/nanofase \
  --baseline output \
  --config config.nml
```

The script writes each candidate run under `verification/runs/`, which is ignored
by git. It does not modify `config.nml` or the baseline output directory.

## What Is Compared

- `output_water.csv`, `output_sediment.csv`, and `output_soil.csv` keep exact
  row/column structure and exact nonnumeric fields. Numeric fields are compared
  with `--atol` and `--rtol`, unless `--exact` is used.
- `summary.md` is compared after filtering the volatile `Simulation datetime`
  line. Numeric tokens use the configured tolerance unless `--exact` is used.
- `output.nc` is compared with `ncdump` after filtering volatile NetCDF `history`
  metadata. Numeric tokens use the configured tolerance unless `--exact` is used.

Raw NetCDF byte identity is not required because metadata can include run-time
timestamps even when model results are unchanged.

## Repeatable WaterBody Checks

`verify_waterbody.py` generates the Phase 7 inputs, captures fresh reference results,
and compares a changed executable with those results. It uses Python's standard
library and the existing `ncdump` and `ncgen` commands; no Python NetCDF package is
needed.

Run from the repository root, using an executable built from unchanged Phase 6
revision `55928ee0c6408174c6d08438c17b3e65a756fc96` with the same compiler, settings,
and original version-file contents as the changed build:

```sh
python3 verification/verify_waterbody.py capture \
  --exe /path/to/phase6/nanofase \
  --work-dir /private/tmp/nanofase-waterbody-check

python3 verification/verify_waterbody.py compare \
  --exe build-debug/nanofase \
  --work-dir /private/tmp/nanofase-waterbody-check
```

Choose a new work directory for each verification run. Reference and candidate
directories cannot be overwritten. Input files are copied into the work directory;
their hashes are checked before comparison. Commands, executable hashes, logs, and
results are saved beside the outputs. The recorded capture revision identifies the
checkout running the script; when the reference executable comes from a different
checkout, record its source revision and compiler settings separately too.

The runner checks fourteen successful scenarios using `verify_refactor.py --exact`,
four expected failures, batch operation, and checkpoint save/reinstate. It checks
that settings actually affect the reference results and that spatial bank-erosion
values override constants. Expected failures retain their exit status and meaningful
error text. Checkpoint checks establish only that saving and loading complete.

Run CTest separately for configuration defaults, error registration and reporting,
and minimum-slope behaviour on an interior reach. Full-model terrain-height outlet
behaviour and disabled river bed sediment remain known failures. See
[the Phase 7 report](../migration_documentation/phase7_waterbody.md) for actual
commands, results, preserved comments, and remaining work.

## Repeatable Reactor Checks

`verify_reactor.py` creates the nine Phase 8 inputs and compares their results
exactly. It uses the helpers in `verify_refactor.py` and `verify_waterbody.py`,
Python's standard library, and `ncdump`.

Build unchanged Phase 7 revision `aaed497723225b05a52c94d101fa4225c998c418`
in a separate checkout with the same compiler, build settings, and original
version-file contents as the changed build. Save its executable, then run:

```sh
python3 -B verification/verify_reactor.py capture \
  --exe /path/to/phase7/nanofase \
  --work-dir /private/tmp/nanofase-reactor-check

python3 -B verification/verify_reactor.py compare \
  --exe build-debug/nanofase \
  --work-dir /private/tmp/nanofase-reactor-check
```

Choose a new work directory for each run. The runner refuses to overwrite existing
reference or candidate directories and checks saved input hashes before comparison.
It records commands, executable hashes, per-case logs, results, and evidence that
each active reaction or shear change affects water output. Record the reference
executable's source revision and compiler settings separately when it comes from
a different checkout; the capture revision identifies the checkout running the script.

The scenarios cover river and estuary references, all four omitted defaults,
each nonzero reaction rate, combined reactions in both water types, and increased
shear. Omitted defaults must reproduce the explicit-default CSV results. Every
before/after comparison uses `verify_refactor.py --exact` for CSV, summary, and
NetCDF output under the timestamp rules above.

For the complete Phase 8 check, also run the WaterBody runner against the same
Phase 7 reference executable in a different work directory, and run CTest. The
WaterBody runner includes the existing expected failures, batch operation, and
checkpoint save/load checks. CTest covers Reactor defaults, error 903 and its
reporting, registration counts, and the current attachment mass-loss result.

The `reactor_known_mass_loss` test intentionally preserves a defect: with two equal
attachment rates, mass falls from 100 to 75 and from 50 to 37.5. It does not establish
correct science. A separate correction must conserve mass and update this test.
See [the Phase 8 report](../migration_documentation/phase8_reactor.md) for actual
results and remaining work.

## Repeatable Biota Checks

`verify_biota.py` compares the concentrations stored in organisms as well as the
ordinary model outputs. The shipped constants have no Biota groups, and the
ordinary outputs do not report organism concentrations, so both kinds of check
are required.

Use unchanged Phase 8 revision `c1e73e0fc41bc1b3568864366933e4638c387812` for the
reference. Build with the same compiler, flags, and saved version-file contents
as the candidate. Two test programs must be identical in both builds:

- `test/BiotaScienceTest.f90` calls the actual soil and water Biota procedures.
- `test/BiotaIntegrationTest.f90` uses normal startup, warm-up, environment updates,
  and batch switching, then records the organisms inside soil layers and reaches.

To build these programs on Phase 8, copy those two test files and append only the
CMake block starting with `# These probes use existing public procedures` and
ending with `add_test(NAME biota_science COMMAND biota_science_test)` to its
original CMake file. Do not copy the separate Biota error-registration target,
which depends on the new Phase 9 module. Give each build its own build directory.
The test programs each have a separate directory for compiled Fortran modules.
Restore the saved version-file contents after configuring and before building.

Run from the candidate repository root:

```sh
python3 -B verification/verify_biota.py capture \
  --exe /path/to/phase8/nanofase \
  --science-exe /path/to/phase8/biota_science_test \
  --integration-exe /path/to/phase8/biota_integration_test \
  --work-dir /private/tmp/nanofase-biota-check

python3 -B verification/verify_biota.py compare \
  --exe build-debug/nanofase \
  --science-exe build-debug/biota_science_test \
  --integration-exe build-debug/biota_integration_test \
  --work-dir /private/tmp/nanofase-biota-check
```

Choose a new work directory for each capture. The runner refuses to overwrite
reference or candidate results, checks that inputs and test sources have not
changed, and records executable hashes, commands, logs, and coverage evidence.
Record the reference source revision and compiler settings separately when its
executables come from a different checkout; the capture revision identifies the
checkout running the script.

The direct test covers creation, all six uptake spellings, the different soil and
water attachment positions, all three material types, storage fractions, zero
growth/death, timestep duration, harvesting, and changed start dates. It emits 50
full-precision concentration records and checks that intended differences occur.

Six integration cases cover absent Biota, soil only, water only, mixed organisms,
the estuary example, and a three-chunk batch crossing February's harvest period
and recovering in March. Each case checks organism counts and selected input
indices, requires evidence of updates, and compares state records exactly. All
six ordinary model output sets also use the existing exact comparison rules.

For a complete Phase 9 check, run CTest and both existing Reactor and WaterBody
runners against the same fresh Phase 8 reference. CTest verifies the full error
registration sequence and that critical error 902 stops only when error output
is enabled. The WaterBody runner retains the four expected failures and the
batch/checkpoint save/load checks.

The checkpoint checks do not establish exact continuation: organism concentrations
are not saved or restored, and the existing warm-up timing issue remains. The
Biota tests also preserve the current one-day-per-step harvest calendar, repeated
resets during the harvest month, and zero-growth/death storage behaviour. Invalid
uptake forms can lead to unset-variable calculations; these unstable numbers are
not used as reference expectations. See [the Phase 9 report](../migration_documentation/phase9_biota.md).
