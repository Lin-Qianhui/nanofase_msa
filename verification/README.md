# Refactor Verification

This folder contains local-only regression checks for behavior-preserving migration
phases. The script runs a NanoFASE executable with a copied config and compares the
new outputs against a baseline generated by the original unrefactored model.

For a new migration phase, capture a fresh reference from the immediately preceding
phase with the same compiler, numerical flags, and effective version label. For
Phase 12 and later, pass the same `-DNANOFASE_VERSION=<label>` to both builds. The historical
examples below describe their original phase comparisons; do not reuse old output
directories as evidence for a different phase.

## Version-Length Correction Checks (Phase 14)

See [the Phase 14 report](../migration_documentation/phase14_version_length.md)
for the saved reference, actual results and reconstruction instructions when no
separate Phase 13 commit is available.

Use a fresh Phase 13 reference, with identical Biota and shared-consumer test
sources and numerical compiler flags. Run all four comparison suites with
`-DNANOFASE_VERSION=migration-check` on both builds. Keep the existing exact
comparison filters and source-hash protections.

The build-version runner now compiles the real ModelConfig and its dependencies.
It checks neutral initial state, clearing, reading configuration twice, and full
labels at lengths 1, 15, 16, 17, 18 and 256, plus long quoted/special-character
labels. It also retains all earlier version selection and build-isolation checks.

For a separately built long-label pair, check the intended old/new metadata before
comparing all other output exactly:

```sh
python3 -B verification/verify_version_outputs.py \
  --reference-exe /path/to/phase13-long-build/nanofase \
  --exe /path/to/phase14-long-build/nanofase \
  --label v0.0.5-phase14-full-version-label-123456789 \
  --work-dir /path/to/new-evidence
```

Both executables must be built with that exact `NANOFASE_VERSION` and matching
compiler flags. This dedicated check tests console, summary, and the complete
NetCDF source text/URL under both layouts and writing modes. It permits only the
explicitly checked version differences and existing datetime/history exclusions;
the general comparison helpers are unchanged. Run the build-route runner too.

For Phase 12's reference, use revision `99522f1f5a66789a9e1fac4b187071aa160f0d81`
and its vendored dependencies in a separate source copy. That older build has no

then build and confirm the file's hash again. If building reconfigured and rewrote
it, restore and build again. Save the four reference programs listed under Phase 11.
The candidate uses `-DNANOFASE_VERSION=0.0.5-18-g163ae42`. Later comparisons where
both revisions include Phase 12 use the same override on both sides, with no source
restoration. Keep the same numerical compiler flags and NetCDF installation.

Run all four existing capture/compare suites with a fresh pre-phase reference,
using the command forms below for Phase 11. They still cover 47 exact output sets,
Biota concentrations, expected failures, batch operation and saved checkpoint state.
Their comparison filters must stay unchanged. Phase 13 updates only the direct
Biota test setup: compile the identical updated source against both Phase 12 and
the candidate before capturing, and retain the existing source-hash checks.
Historical Phase 8/9 comparisons use their original test sources.

Two additional runners check the build routes:

```sh
python3 -B verification/verify_build_system.py \
  --compiler gfortran-14 --work-dir /private/tmp/nanofase-version-checks
python3 -B verification/verify_build_routes.py \
  --compiler gfortran-14 --work-dir /private/tmp/nanofase-route-checks
ctest --test-dir /path/to/candidate-build --output-on-failure
```

Use the compiler matching your NetCDF installation; `gfortran-14` is the compiler
used for the recorded Phase 12 checks, not a new project requirement. Both runners
create a fresh evidence directory on every invocation and save commands and results.

The first runner uses small Fortran programs and the actual CMake version helper.
Its 19 check groups cover complete labels, quoting, real ModelConfig reset and
initialisation, length boundaries, long generated-source lines, independent build directories,
unchanged builds, cleared overrides, Git commits/tags, unavailable Git, missing tags,
archives inside another repository, worktrees, direct secondary-target builds, old
compiled-module migration, and unchanged source hashes. It is also one CTest case
when Python is available. Its timed edits account for the older macOS Make tool's
whole-second file timestamp comparisons.

The second runner builds the full model using automatic CMake selection, all three
Make modes, clean/rebuild, a source archive, and the package recipe's `fpm @install`
command into a temporary prefix. It checks console/summary/NetCDF labels and source
hashes around every command. It needs `nf-config`, `ncdump`, Make, CMake, fpm, Git,
and the existing example inputs. It copies available fpm dependency caches into
its isolated archive; otherwise fpm may need network access. It does not require
numerical identity between different optimization profiles.

Run these checks without editing source or documentation at the same time: the
full-build runner deliberately fails if tracked-file hashes change. Main and test
compiled-module directories are separate; old build-root module files are retained
under `legacy-fortran-modules` to prevent stale imports. Compiler module files are
build products, not tracked source.

See [the Phase 12 report](../migration_documentation/phase12_build_system_cleanup.md)
for actual results and remaining work. Historical instructions below retain their
original reference revisions and the source-restoration procedure they required.

## Baseline Setup

The current `output/` directory can be used as the baseline if it was generated by
the original model from the tracked `config.nml`.

For exact checks, the baseline should come from the same compiler and build
settings used for the refactor comparison. If the baseline was produced from a
different source revision or build configuration, tiny floating-point formatting
differences may still cause a useful failure.

For a safer long-term baseline, copy it once:

```sh
mkdir -p verification/baselines/original_config_nml
cp -R output/. verification/baselines/original_config_nml/
```

`verification/baselines/` is ignored by git because the outputs are large.

## Run Verification

From the repository root:

```sh
python verification/verify_refactor.py \
  --exe build-debug/nanofase \
  --baseline verification/baselines/original_config_nml \
  --config config.nml
```

By default, numeric comparisons use:

```text
absolute tolerance: 1e-14
relative tolerance: 1e-12
```

Override those gates when a phase needs a documented tolerance:

```sh
python verification/verify_refactor.py \
  --exe build-debug/nanofase \
  --baseline verification/baselines/original_config_nml \
  --config config.nml \
  --atol 1e-12 \
  --rtol 1e-9
```

Use `--exact` to restore the original strict mode: CSV files must be
byte-identical, and filtered `summary.md`/`output.nc` text must match exactly.

You can also compare directly against the existing `output/` baseline:

```sh
python verification/verify_refactor.py \
  --exe build-debug/nanofase \
  --baseline output \
  --config config.nml
```

The script writes each candidate run under `verification/runs/`, which is ignored
by git. It does not modify `config.nml` or the baseline output directory.

## What Is Compared

- `output_water.csv`, `output_sediment.csv`, and `output_soil.csv` keep exact
  row/column structure and exact nonnumeric fields. Numeric fields are compared
  with `--atol` and `--rtol`, unless `--exact` is used.
- `summary.md` is compared after filtering the volatile `Simulation datetime`
  line. Numeric tokens use the configured tolerance unless `--exact` is used.
- `output.nc` is compared with `ncdump` after filtering volatile NetCDF `history`
  metadata. Numeric tokens use the configured tolerance unless `--exact` is used.

Raw NetCDF byte identity is not required because metadata can include run-time
timestamps even when model results are unchanged.

## Diagnostic-Registry Correction Checks (Phase 11)

The registry is the list of available error codes and messages. Phase 11 restores
WaterBody warning 405 and moves critical code 901 from shared setup to WaterBody
setup. Codes 110/200/201/300 remain shared. Blank positions 4 and 5 deliberately
keep code 1's blank critical message. Scientific results must remain identical;
the new diagnostic tests check the intended reporting changes directly.

Use a fresh Phase 10 reference from revision
`cf0e904c8bb2044bcded305743b316288efb19c5`, with the same compiler, flags, and
saved version-file contents as the candidate. Do not reuse the older phase outputs
described later in this guide. Build and save `nanofase`,
`shared_consumer_integration_test`, `biota_science_test`, and
`biota_integration_test` before editing production code. All four programs already
exist in Phase 10; no comparison-test source needs to be copied or changed.

After each CMake configuration, restore the exact saved `src/VersionModule.f90`
contents before building. Save build settings, executable hashes, commands, and
logs in a new directory outside tracked source folders.

Run the complete tests after building the candidate:

```sh
ctest --test-dir build-debug --output-on-failure
```

The shared-handler and domain tests check the complete expected code set without
duplicates, exact messages, severity, and counts 15/16/17/25/26/27 through shared,
Soil, BedSediment, WaterBody, Reactor, and Biota setup. Codes 405 and 901 must be
absent before WaterBody setup. Reactor and Biota must preserve prior definitions.

The added reporting cases run in separate processes:

- `shared_error_*` checks codes 1/110/200/201/300 with error output enabled, warnings
  suppressed, and error output disabled. `shared_error_generic` checks a trigger
  with no arguments. Code 1 must print a blank-message error rather than the
  library's default generic text.
- `water_body_warning405_code`, `water_body_warning405_instance`, and
  `water_body_warning405_array` require exactly one full warning line and successful
  continued execution. The latter two use the registered error, which carries its
  warning status; a newly constructed `ErrorInstance` is critical by default.
- `water_body_quiet_405` and `water_body_disabled_405` require silent continuation.
  `water_body_critical901` and `water_body_quiet_901` require the full error message
  and exit 1. `water_body_disabled_901` requires silent continuation.

The wrappers check exit status and completion markers, remove only the known
console color sequences when checking text, and do not compare runtime addresses
or source-line numbers. Registration and reporting tests do not add production
river-length or river-type checks: neither 405 nor 901 currently has a raising site.

For scientific comparisons, use the four existing capture/compare runners. Set
`phase11_evidence` to a new absolute directory and place the saved reference
programs there with `reference_` prefixed to their names. Run from the repository
root, capturing before production edits:

```sh
for suite in waterbody reactor; do
  python3 -B "verification/verify_${suite}.py" capture \
    --exe "$phase11_evidence/reference_nanofase" \
    --work-dir "$phase11_evidence/${suite}_checks"
done
python3 -B verification/verify_biota.py capture \
  --exe "$phase11_evidence/reference_nanofase" \
  --science-exe "$phase11_evidence/reference_biota_science_test" \
  --integration-exe "$phase11_evidence/reference_biota_integration_test" \
  --work-dir "$phase11_evidence/biota_checks"
python3 -B verification/verify_shared_consumers.py capture \
  --exe "$phase11_evidence/reference_nanofase" \
  --probe-exe "$phase11_evidence/reference_shared_consumer_integration_test" \
  --work-dir "$phase11_evidence/shared_consumers_checks"
```

After the candidate build, run each command again with `capture` changed to
`compare`, the same work directories, and each executable changed to its
corresponding `build-debug/` path. Keep the integration-test sources unchanged;
their existing source-hash protections remain active.

Together these runners cover 47 exact ordinary-output comparisons, direct and
running-model organism concentrations, expected failures, logging, batch runs,
and checkpoint checks. Retain their existing strict comparison rules. Checkpoint
checks establish saved-state restoration, not correct continuation of a simulation.
The [Phase 11 report](../migration_documentation/phase11_diagnostic_registry.md)
records the actual commands, results, comment checks, and remaining work.

## Repeatable Shared-Consumer Checks (Phase 10)

`verify_shared_consumers.py` checks output choices that the original fixed-filename
comparison does not cover. It checks the complete expected file set, including
disabled files, filename suffixes, statistics, and steady-state output. CSV files
are compared byte-for-byte; summaries exclude only `Simulation datetime`, and
NetCDF dumps exclude only `history`. The older comparison script and runners keep
their original interfaces and strict rules.

Use unchanged Phase 9 revision `78d9c61` as the reference. Build it with the same
compiler, flags, and saved version-file contents as the candidate. Copy
`test/SharedConsumerIntegrationTest.f90` to the reference tree and append only the
CMake block starting with `# Read the same input/checkpoint state` and ending with
the `target_link_libraries(shared_consumer_integration_test ...)` call. Build the
`nanofase` and `shared_consumer_integration_test` targets. Do not copy the following
`shared_consumer_module_test` target into Phase 9: it deliberately tests the new
default owner and direct access without copying values to `C`.

Restore the saved `src/VersionModule.f90` contents after each CMake configuration,
before building. Give each source tree its own build directory. Run from the
candidate repository root, with a new evidence directory:

```sh
python3 -B verification/verify_shared_consumers.py capture \
  --exe /path/to/phase9/nanofase \
  --probe-exe /path/to/phase9/shared_consumer_integration_test \
  --work-dir /private/tmp/nanofase-shared-check

python3 -B verification/verify_shared_consumers.py compare \
  --exe build-debug/nanofase \
  --probe-exe build-debug/shared_consumer_integration_test \
  --work-dir /private/tmp/nanofase-shared-check

ctest --test-dir build-debug --output-on-failure
```

Both integration programs must be built from the identical test source. The runner
checks its hash and the copied input hashes, saves commands and executable hashes,
and refuses to overwrite either stage, including a failed stage. Record the actual
reference revision and build settings separately when using another source tree.

The checks cover 18 complete model-output scenarios, four startup diagnostic cases,
and six checkpoint cases. They exercise both NetCDF writing modes and output
layouts, optional columns and units, logging and colors, a one-cell simulation
mask, and batch changes in paths, constants, dates, and 10/11/10-step lengths.
Column checks require enabled details and reject disabled ones. They check soil
concentration-unit labels explicitly; the existing sediment writer always emits
both units, independently of its unit setting.
The state program verifies that missing evaporation is replaced with correctly
sized zero arrays. Logs use the same execution paths in both stages; only timestamps
and measured CPU/wall durations are removed for comparison.

Statistics currently creates an empty file; the runner explicitly preserves and
compares it. The steady-state case stops after one iteration and proves only the
migrated output path. Checkpoint cases load the pre-phase file, check nonzero `t0`
with preservation on/off, and check grid differences inside/outside the tolerance.
Tolerance fixtures zero two values in a copy of the checkpoint header, allowing
tiny perturbations to survive normal-real rounding without changing model settings.
These files use the existing native gfortran record layout; no new portable
checkpoint format is claimed. Comparisons check record sizes and all defined saved
values. Unused reach positions in water volume, bed area, and sediment arrays are
excluded because the existing writer does not initialise them; raw checkpoint bytes
are therefore not a stable reference. The main loop still ignores restored `t0`,
and Biota concentrations remain absent from checkpoints.

CTest additionally checks defaults, repeated initialisation, required groups,
utility boundaries and array shapes, logger settings, and the shared defaults
compatibility export. The new direct tests leave `C` untouched. The existing Biota
comparison test retains its deliberate historical compatibility setup unchanged.

For the full phase checks, also capture/compare WaterBody, Reactor, and Biota using
the same fresh Phase 9 executable and its Biota test programs. Do not substitute
their older documented reference revisions for this phase. See the
[Phase 10 report](../migration_documentation/phase10_shared_consumers.md) for actual
results, original-comment checks, and remaining work.

## Repeatable WaterBody Checks

`verify_waterbody.py` generates the Phase 7 inputs, captures fresh reference results,
and compares a changed executable with those results. It uses Python's standard
library and the existing `ncdump` and `ncgen` commands; no Python NetCDF package is
needed.

Run from the repository root, using an executable built from unchanged Phase 6
revision `55928ee0c6408174c6d08438c17b3e65a756fc96` with the same compiler, settings,
and original version-file contents as the changed build:

```sh
python3 verification/verify_waterbody.py capture \
  --exe /path/to/phase6/nanofase \
  --work-dir /private/tmp/nanofase-waterbody-check

python3 verification/verify_waterbody.py compare \
  --exe build-debug/nanofase \
  --work-dir /private/tmp/nanofase-waterbody-check
```

Choose a new work directory for each verification run. Reference and candidate
directories cannot be overwritten. Input files are copied into the work directory;
their hashes are checked before comparison. Commands, executable hashes, logs, and
results are saved beside the outputs. The recorded capture revision identifies the
checkout running the script; when the reference executable comes from a different
checkout, record its source revision and compiler settings separately too.

The runner checks fourteen successful scenarios using `verify_refactor.py --exact`,
four expected failures, batch operation, and checkpoint save/reinstate. It checks
that settings actually affect the reference results and that spatial bank-erosion
values override constants. Expected failures retain their exit status and meaningful
error text. Checkpoint checks establish only that saving and loading complete.

Run CTest separately for configuration defaults, error registration and reporting,
and minimum-slope behaviour on an interior reach. Full-model terrain-height outlet
behaviour and disabled river bed sediment remain known failures. See
[the Phase 7 report](../migration_documentation/phase7_waterbody.md) for actual
commands, results, preserved comments, and remaining work.

Build unchanged Phase 7 revision `aaed497723225b05a52c94d101fa4225c998c418`

Choose a new work directory for each run. The runner refuses to overwrite existing

## Repeatable Biota Checks

`verify_biota.py` compares the concentrations stored in organisms as well as the
ordinary model outputs. The shipped constants have no Biota groups, and the
ordinary outputs do not report organism concentrations, so both kinds of check
are required.

Use unchanged Phase 8 revision `c1e73e0fc41bc1b3568864366933e4638c387812` for the
reference. Build with the same compiler, flags, and saved version-file contents
as the candidate. Two test programs must be identical in both builds:

- `test/BiotaScienceTest.f90` calls the actual soil and water Biota procedures.
- `test/BiotaIntegrationTest.f90` uses normal startup, warm-up, environment updates,
  and batch switching, then records the organisms inside soil layers and reaches.

To build these programs on Phase 8, copy those two test files and append only the
CMake block starting with `# These probes use existing public procedures` and
ending with `add_test(NAME biota_science COMMAND biota_science_test)` to its
original CMake file. Do not copy the separate Biota error-registration target,
which depends on the new Phase 9 module. Give each build its own build directory.
The test programs each have a separate directory for compiled Fortran modules.
Restore the saved version-file contents after configuring and before building.

Run from the candidate repository root:

```sh
python3 -B verification/verify_biota.py capture \
  --exe /path/to/phase8/nanofase \
  --science-exe /path/to/phase8/biota_science_test \
  --integration-exe /path/to/phase8/biota_integration_test \
  --work-dir /private/tmp/nanofase-biota-check

python3 -B verification/verify_biota.py compare \
  --exe build-debug/nanofase \
  --science-exe build-debug/biota_science_test \
  --integration-exe build-debug/biota_integration_test \
  --work-dir /private/tmp/nanofase-biota-check
```

Choose a new work directory for each capture. The runner refuses to overwrite
reference or candidate results, checks that inputs and test sources have not
changed, and records executable hashes, commands, logs, and coverage evidence.
Record the reference source revision and compiler settings separately when its
executables come from a different checkout; the capture revision identifies the
checkout running the script.

The direct test covers creation, all six uptake spellings, the different soil and
water attachment positions, all three material types, storage fractions, zero
growth/death, timestep duration, harvesting, and changed start dates. It emits 50
full-precision concentration records and checks that intended differences occur.

Six integration cases cover absent Biota, soil only, water only, mixed organisms,
the estuary example, and a three-chunk batch crossing February's harvest period
and recovering in March. Each case checks organism counts and selected input
indices, requires evidence of updates, and compares state records exactly. All
six ordinary model output sets also use the existing exact comparison rules.

For a complete Phase 9 check, run CTest and both existing Reactor and WaterBody
runners against the same fresh Phase 8 reference. CTest verifies the full error
registration sequence and that critical error 902 stops only when error output
is enabled. The WaterBody runner retains the four expected failures and the
batch/checkpoint save/load checks.

The checkpoint checks do not establish exact continuation: organism concentrations
are not saved or restored, and the existing warm-up timing issue remains. The
Biota tests also preserve the current one-day-per-step harvest calendar, repeated
resets during the harvest month, and zero-growth/death storage behaviour. Invalid
uptake forms can lead to unset-variable calculations; these unstable numbers are
not used as reference expectations. See [the Phase 9 report](../migration_documentation/phase9_biota.md).
