# Refactor Verification

This folder contains local-only regression checks for behavior-preserving migration
phases. The script runs a NanoFASE executable with a copied config and compares the
new outputs against a baseline generated by the original unrefactored model.

## Baseline Setup

The current `output/` directory can be used as the baseline if it was generated by
the original model from the tracked `config.nml`.

For exact checks, the baseline should come from the same compiler and build
settings used for the refactor comparison. If the baseline was produced from a
different source revision or build configuration, tiny floating-point formatting
differences may still cause a useful failure.

For a safer long-term baseline, copy it once:

```sh
mkdir -p verification/baselines/original_config_nml
cp -R output/. verification/baselines/original_config_nml/
```

`verification/baselines/` is ignored by git because the outputs are large.

## Run Verification

From the repository root:

```sh
python verification/verify_refactor.py \
  --exe build-debug/nanofase \
  --baseline verification/baselines/original_config_nml \
  --config config.nml
```

By default, numeric comparisons use:

```text
absolute tolerance: 1e-14
relative tolerance: 1e-12
```

Override those gates when a phase needs a documented tolerance:

```sh
python verification/verify_refactor.py \
  --exe build-debug/nanofase \
  --baseline verification/baselines/original_config_nml \
  --config config.nml \
  --atol 1e-12 \
  --rtol 1e-9
```

Use `--exact` to restore the original strict mode: CSV files must be
byte-identical, and filtered `summary.md`/`output.nc` text must match exactly.

You can also compare directly against the existing `output/` baseline:

```sh
python verification/verify_refactor.py \
  --exe build-debug/nanofase \
  --baseline output \
  --config config.nml
```

The script writes each candidate run under `verification/runs/`, which is ignored
by git. It does not modify `config.nml` or the baseline output directory.

## What Is Compared

- `output_water.csv`, `output_sediment.csv`, and `output_soil.csv` keep exact
  row/column structure and exact nonnumeric fields. Numeric fields are compared
  with `--atol` and `--rtol`, unless `--exact` is used.
- `summary.md` is compared after filtering the volatile `Simulation datetime`
  line. Numeric tokens use the configured tolerance unless `--exact` is used.
- `output.nc` is compared with `ncdump` after filtering volatile NetCDF `history`
  metadata. Numeric tokens use the configured tolerance unless `--exact` is used.

Raw NetCDF byte identity is not required because metadata can include run-time
timestamps even when model results are unchanged.

## Repeatable WaterBody Checks

`verify_waterbody.py` generates the Phase 7 inputs, captures fresh reference results,
and compares a changed executable with those results. It uses Python's standard
library and the existing `ncdump` and `ncgen` commands; no Python NetCDF package is
needed.

Run from the repository root, using an executable built from unchanged Phase 6
revision `55928ee0c6408174c6d08438c17b3e65a756fc96` with the same compiler, settings,
and original version-file contents as the changed build:

```sh
python3 verification/verify_waterbody.py capture \
  --exe /path/to/phase6/nanofase \
  --work-dir /private/tmp/nanofase-waterbody-check

python3 verification/verify_waterbody.py compare \
  --exe build-debug/nanofase \
  --work-dir /private/tmp/nanofase-waterbody-check
```

Choose a new work directory for each verification run. Reference and candidate
directories cannot be overwritten. Input files are copied into the work directory;
their hashes are checked before comparison. Commands, executable hashes, logs, and
results are saved beside the outputs. The recorded capture revision identifies the
checkout running the script; when the reference executable comes from a different
checkout, record its source revision and compiler settings separately too.

The runner checks fourteen successful scenarios using `verify_refactor.py --exact`,
four expected failures, batch operation, and checkpoint save/reinstate. It checks
that settings actually affect the reference results and that spatial bank-erosion
values override constants. Expected failures retain their exit status and meaningful
error text. Checkpoint checks establish only that saving and loading complete.

Run CTest separately for configuration defaults, error registration and reporting,
and minimum-slope behaviour on an interior reach. Full-model terrain-height outlet
behaviour and disabled river bed sediment remain known failures. See
[the Phase 7 report](../migration_documentation/phase7_waterbody.md) for actual
commands, results, preserved comments, and remaining work.
